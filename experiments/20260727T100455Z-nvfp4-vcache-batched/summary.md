# KLD Baseline Data Comparison Results

This summary is generated by `tools/kld/scripts/parse-kld-results.py`.

## Experiment conclusion

`GGML_CUDA_NVFP4_VCACHE_BATCHED=1` preserves the observed quality of the
current native-slice implementation while materially reducing V-cache P*V
overhead. The focused KLD results below are identical at every reported metric,
and the repository V-cache correctness suite passes with the switch both unset
and enabled.

The implementation keeps the current numerical sequence:

- compute one P `amax` and dynamic NVFP4 global scale per `(stream, query head, column)` row;
- encode the original V block scale byte into the cuBLASLt A scale channel;
- apply the combined F32 compensation `1 / (V_global_scale * P_global_scale)` after matmul.

Only scheduling and materialization changed: all P rows are quantized together,
unique KV-head/stream V slices are repacked together, all P slices are repacked
together, scratch is allocated once, and cuBLASLt descriptors/layouts are
created once per P*V operation.

## Quality comparison

The native-slice and batched cases produced identical reported results across
all eight KLD chunks:

- mean KLD: `0.078243 +/- 0.004257`;
- 99.9% KLD: `2.182183`;
- PPL(Q): `10.72598 +/- 0.72955`;
- PPL ratio versus f16/f16 baseline: `1.019927 +/- 0.012474`;
- RMS delta-p: `8.029% +/- 0.449%`;
- same-top-p: `87.843% +/- 0.724%`.

This is evidence that the optimization did not add a measurable precision
difference relative to the current native-slice path for this workload; it is
not a claim that NVFP4 V-cache itself matches f16 V-cache.
